# 기술 스택 선정 문서

## 1. 기술 스택 요약

| 영역 | 기술 | 사용 목적 |
|---|---|---|
| Frontend | React | 화면 구성과 사용자 인터랙션 구현 |
| Frontend | TypeScript | 타입 기반 코드 안정성 확보 |
| Frontend | Vite | 프론트엔드 개발 서버와 빌드 도구 |
| Backend | Spring Boot | REST API 서버 구현 |
| Backend | Spring Security OAuth2 | Google 소셜 로그인 연동 |
| Database | PostgreSQL | 사용자, 문제, 결과, 랭킹 데이터 저장 |
| Infra | Docker Compose | 로컬 개발용 DB 실행 환경 구성 |
| Version Control | Git, GitHub | 버전 관리와 포트폴리오 공개 |

## 2. Frontend

### React

| 항목 | 내용 |
|---|---|
| 사용 목적 | 홈, 카테고리 선택, 퀴즈 풀이, 결과, 랭킹 화면 구현 |
| 선택 이유 | 컴포넌트 단위로 화면을 나누기 쉽고, 포트폴리오에서 활용도가 높은 프론트엔드 라이브러리입니다. |
| 대체 후보 | Vue, Svelte, 일반 HTML/CSS/JavaScript |
| 도입 범위 | 초기 버전에서는 React 기본 기능과 React Router 중심으로 사용합니다. |
| 주의점 | 상태 관리가 복잡해지지 않도록 전역 상태 관리 라이브러리는 초기 버전에서 도입하지 않습니다. |

### TypeScript

| 항목 | 내용 |
|---|---|
| 사용 목적 | API 응답, 퀴즈 문제, 사용자 정보 등의 데이터 구조를 명확히 정의 |
| 선택 이유 | JavaScript보다 타입 안정성이 높아 실수를 줄이고, 프론트엔드와 백엔드의 데이터 구조를 맞추기 쉽습니다. |
| 대체 후보 | JavaScript |
| 도입 범위 | 화면 컴포넌트, API 응답 타입, 공통 타입 정의에 사용합니다. |
| 주의점 | 타입 정의가 과도하게 복잡해지지 않도록 프로젝트에 필요한 범위에서만 사용합니다. |

### Vite

| 항목 | 내용 |
|---|---|
| 사용 목적 | React 개발 서버 실행과 배포용 빌드 |
| 선택 이유 | 설정이 간단하고 실행 속도가 빠르며, React + TypeScript 프로젝트를 시작하기 쉽습니다. |
| 대체 후보 | Create React App, Next.js, Webpack 직접 구성 |
| 도입 범위 | 프론트엔드 개발 서버와 정적 빌드에 사용합니다. |
| 주의점 | Vite는 백엔드 서버가 아니므로 API 서버는 Spring Boot와 분리해서 구성합니다. |

## 3. Backend

### Spring Boot

| 항목 | 내용 |
|---|---|
| 사용 목적 | 로그인, 퀴즈 문제 조회, 결과 저장, 랭킹 조회 API 구현 |
| 선택 이유 | Java 기반 웹 백엔드 구조를 학습하기 좋고, REST API와 DB 연동을 체계적으로 구현할 수 있습니다. |
| 대체 후보 | Express, NestJS, Django, FastAPI |
| 도입 범위 | REST API 서버, 비즈니스 로직, DB 연동에 사용합니다. |
| 주의점 | 기능이 커지지 않도록 초기 버전에서는 API 범위를 퀴즈 흐름에 필요한 기능으로 제한합니다. |

### Spring Security OAuth2

| 항목 | 내용 |
|---|---|
| 사용 목적 | Google 소셜 로그인 구현 |
| 선택 이유 | Spring Boot에서 OAuth2 로그인 흐름을 표준 방식으로 구현할 수 있습니다. |
| 대체 후보 | 직접 JWT 로그인 구현, Firebase Authentication, Auth0 |
| 도입 범위 | Google 로그인, 사용자 식별, 보호 API 접근 제어에 사용합니다. |
| 주의점 | OAuth Client ID와 Secret은 코드에 직접 작성하지 않고 환경 변수로 관리합니다. |

## 4. Database

### PostgreSQL

| 항목 | 내용 |
|---|---|
| 사용 목적 | 사용자, 퀴즈 문제, 퀴즈 결과, 랭킹 데이터 저장 |
| 선택 이유 | 실제 서비스에서 자주 사용되는 관계형 데이터베이스이며, 데이터 관계를 명확히 설계하기 좋습니다. |
| 대체 후보 | MySQL, MariaDB, H2 |
| 도입 범위 | 로컬 개발과 포트폴리오 시연용 DB로 사용합니다. |
| 주의점 | 초기 개발 편의성을 위해 Docker Compose로 실행하고, 환경 변수로 접속 정보를 관리합니다. |

## 5. Infra / Dev

### Docker Compose

| 항목 | 내용 |
|---|---|
| 사용 목적 | 로컬 개발용 PostgreSQL 컨테이너 실행 |
| 선택 이유 | 로컬 PC에 DB를 직접 설치하지 않아도 동일한 실행 환경을 구성할 수 있습니다. |
| 대체 후보 | 로컬 PostgreSQL 직접 설치, H2 인메모리 DB |
| 도입 범위 | PostgreSQL 실행에 사용합니다. |
| 주의점 | 초기 버전에서는 프론트엔드와 백엔드까지 모두 컨테이너화하지 않고, DB 실행에만 사용합니다. |

### Git / GitHub

| 항목 | 내용 |
|---|---|
| 사용 목적 | 프로젝트 버전 관리와 포트폴리오 공개 |
| 선택 이유 | 변경 이력을 관리하고, 문서와 코드를 GitHub에서 확인할 수 있게 합니다. |
| 대체 후보 | GitLab, Bitbucket |
| 도입 범위 | 문서 작성, 기능 개발, 브랜치 관리, 커밋 기록 관리에 사용합니다. |
| 주의점 | 기능 단위로 커밋하고, 민감한 설정 파일은 커밋하지 않습니다. |

## 6. 도입하지 않는 기술

| 기술 | 제외 이유 |
|---|---|
| Next.js | 서버 렌더링이나 풀스택 프레임워크 기능이 초기 버전에는 필요하지 않습니다. |
| Redux | 초기 상태 관리 범위가 작아 React 기본 상태 관리로 충분합니다. |
| OpenAI API | 관리자 페이지나 문제 검토 흐름이 없는 초기 버전에서는 기능 흐름이 애매해 제외합니다. |
| Kubernetes | 로컬 개발과 포트폴리오 시연에는 과한 인프라입니다. |
| 다중 소셜 로그인 | Google 로그인 하나로 인증 흐름을 먼저 완성합니다. |

## 7. 기술 선택 기준

- 초기 버전에서 완성 가능한 범위를 우선합니다.
- 포트폴리오에서 설명하기 쉬운 구조를 선택합니다.
- 프론트엔드, 백엔드, DB, 인증 흐름을 각각 경험할 수 있게 구성합니다.
- 기능보다 기술 도입이 앞서지 않도록, 실제 요구사항에 필요한 기술만 사용합니다.
- 민감한 설정값은 코드에 직접 넣지 않고 환경 변수로 관리합니다.
